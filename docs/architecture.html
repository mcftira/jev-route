jev-route

A calibrated router that sends each LLM request to the cheapest model that can safely answer it. It decides with probability distributions rather than a single label, keeps sensitive data inside your own infrastructure, and logs every decision so you can eventually replace the thing it depends on.

01

The request path

One request, eight stages, in a fixed order. The order is the design: the gate runs before any model is consulted, because a model cannot be asked whether something is safe to send to a model. The gate itself is two local layers — deterministic, then semantic — and both stay inside the process. Colour marks where data is allowed to go — read the red rows as the only places anything leaves the building.

1

Normalise & excerpt

Messages or a raw string become one bounded excerpt. Nothing is sent anywhere yet.

router.py · prompts.excerpt_messages / excerpt_from_text
2

Local gate, two layers never bypassed

Layer ① is deterministic: regex and checksum detectors run on the raw excerpt — before redaction, so redaction cannot hide a match from it. Findings set sensitivity floors and can force the local tier and block the cloud backend outright. No model is consulted, no network call is made, and the same input always produces the same verdict. Layer ② is a distilled semantic model, local as well: it catches the contextual sensitivity layer ① cannot see. Shadow by default — it scores, records, never blocks; enforce mode can raise the floor and force local, and only after measured criteria passed at construction. Layer ① remains the floor whatever layer ② says.

gate.py · HardGate.scan → GateVerdict · gate_semantic.py · SemanticLayer
3

Redact & fingerprint

Anything that may leave the process is redacted; the raw excerpt is reduced to a salted 16-hex digest. Caller metadata is filtered by an unsafe-key list as well as by type, because {"prompt": "…"} is a scalar and would otherwise ride along into the log.

prompts.py · redact / hash_text / compute_features / safe_caller_metadata
TRUST BOUNDARY  —  only the redacted excerpt + features + allowlisted metadata may cross, and only if the gate did not block. If the gate fired, nothing crosses at all.
4

Cache, then ask the decision backend

The cache stores the backend’s judgement, not the final decision — so a policy change applies immediately to cached traffic instead of being frozen behind it. On a miss the backend answers with full soft distributions. A backend outage degrades to maximum uncertainty; it never raises into the request path.

cache.py · backends/* → BackendResult(answers, degraded, latency_ms)
5

Merge the gate floor over the answer

Maximum, never minimum. A model saying “public” cannot outvote a deterministic finding of “regulated”, and a layer ② that answers “public” contributes nothing — resolve_floor is a maximum over the layers, so both gate layers can only ever make routing stricter.

router.py · schema.bump_within over SENSITIVITY_LEVELS
6

Escalate on low confidence

Uncertainty is only ever resolved upward. Below a confidence threshold the answer is bumped one level; below a much lower “too uncertain to egress” floor it goes straight to the safest tier. Both thresholds are calibrated against measurement, not taste.

policy.UncertaintyPolicy · router.py stage 6
7

Resolve tier & model

A safe-AST rule engine — no eval, no calls, no attribute access — picks the first matching rule. Data protection rules precede capability rules, so a hard task on regulated data is still regulated.

policy.py · Policy.evaluate → (rule, tier, model)
8

Log the decision this is the dataset

Every decision is appended with its full soft distributions, not just the argmax. That single choice is what turns an audit log into training data — a label tells you what the teacher picked, a distribution tells you how sure it was.

logging_sink.py · schema.DecisionRecord (schema-versioned JSONL)
stays local / deterministic may cross the boundary egress risk trust boundary

03

The two-layer gate

The bootstrap paradox
The gate cannot ask the cloud whether something is safe to send to the cloud.

Everything about this layer follows from that sentence. The deterministic floor never asks a model, because the model call is the thing being guarded. And the semantic model is trained only on synthetic and public positives plus real production negatives — never on real blocked content. The gate never trains on your secrets.

①

Deterministic floor permanent

Regex and checksums: Luhn-validated card numbers, IBAN mod-97, SSN, MRN, credentials, basic-auth URLs. Auditable, reproducible, and it never asks a model. It is never removed — a semantic layer is a statistical model and the floor is a checksum, and where a false negative means data left the building you do not retire the checksum because the model got good.

②

Distilled semantic layer shadow by default

A local model that catches contextual sensitivity regex cannot see — an HR disciplinary narrative, a legal privilege discussion, a clinical note in prose. None of those contains a single detectable identifier. It runs, scores, and logs disagreements with layer ①, and it never blocks until it has earned promotion.

③

Router

JevBackend now; DistilledBackend after graduation. Stage 5 above merges the floor over whatever this returns, by maximum.

Hard findings vs advisory topics

Structured identifiers and credentials set floors. Topic keywords (HIPAA, PCI, GDPR) are advisory hints only and never move a floor. Collapsing the two is exactly how regex guardrails end up air-gapping every compliance question — so “explain how HIPAA works” routes to the cheap cloud tier while a chart containing an SSN never leaves the building. Both behaviours are verified against the live cluster.

Promotion to enforce is earned, not configured

A config flag alone must not be sufficient. Promotion requires measured recall on a held-out positive set, a bounded false-positive rate on real negatives, and a bounded disagreement rate against layer ①. If the criteria are not met the router refuses loudly, with the numbers rather than silently degrading to shadow — a silent downgrade is how a gate that looks enforced stops being enforced.

04

Graduation — two separate tracks

The router and the gate learn from different data and have different failure modes, so they graduate separately with separate readiness criteria. Conflating them is how a project ends up claiming the gate is “trained on your traffic” when it cannot be.

Why the synthetic data has to be provably fake, not just randomised

A randomised 3-digit SSN area collides with real issued ranges — so “synthetic” would silently mean “possibly somebody’s actual data”, and the entire argument collapses. The generator therefore uses values reserved by the issuing authority: SSN areas 000, 666 and 900–999 (the SSA will never issue them), RFC 2606 reserved email domains, and the reserved fictional telephone block.

Payment cards carry a real tension worth knowing about. A Luhn-invalid number is provably not a real card — but layer ① validates cards with Luhn, so Luhn-invalid synthetic cards never fire it, and layer-① recall becomes untestable. Published provider test ranges resolve this: Luhn-valid, publicly reserved, provably not a cardholder’s data, and still caught by the floor.

05

Deployment topology

Verified live on a k3s cluster. The router ships as a ConfigMap-mounted source tree with PYTHONPATH=/app — no custom image, no registry. LiteLLM loads it as a pre-call hook, so clients just call the model alias auto and never learn routing exists.

Deployed with python deploy/k8s/deploy.py --context spark-local. Two traps are handled in that script and documented in deploy/k8s/README.md: client-side kubectl apply cannot carry a ConfigMap this large (256 KiB annotation cap), so it uses server-side apply; and Kubernetes does not restart pods when a mounted ConfigMap changes, so the script stamps a content checksum into the pod template. Without the second one, a policy edit redeploys “successfully” and changes nothing.

07

The honest trade, and the honest limits

Safety costs accuracy, and the knob is measured

On the same 223 prompts with uncertainty escalation on: tier accuracy 72.2%, 11 privacy violations. Off: accuracy 83.4%, 23 violations. Escalation buys a 52% reduction in violations — 23 down to 11 — for 11.2 points of accuracy. That is the price of the safety property, stated plainly.

The threshold force_local_confidence_below: 0.25 was not chosen by taste. A sweep over the real certainty distribution shows every value above 0.25 has a negative trade; the sweep is documented in the code next to the constant so the next person can re-run it rather than re-litigate it.

Routing is verified from the log, not the response

Both cloud tiers are reasoning models; qwen3.8-max has taken over ten minutes on a hard prompt. The hook decides and logs in a pre-call hook, before the upstream is contacted, so the decision record is authoritative and a slow upstream cannot mask a correct routing decision. Live-cluster verification: 7/7 routing, 6/6 privacy, all three tiers exercised.

What this does not give you

The semantic layer cannot be trained on your own real sensitive traffic — that is the whole point of the bootstrap paradox. So its recall on your data is inferred from synthetic and public positives plus your clean negatives, not measured on your actual secrets. Shadow-mode disagreement rates on your own traffic are the real evidence, which is precisely why shadow mode exists and why promotion is gated on measurement. Do not read a green test suite as a claim that the gate knows your data.

Equally: 72.2% tier accuracy against a 223-prompt labelled set is a small-sample measurement with a wide confidence interval, not a benchmark score. The privacy-violation count is the number to act on, because it is a floor violation rather than a ranking error.

Works today

Full request path, policy engine, decision log, CLI (including the two-track graduate and label-sensitivity), all three LiteLLM integration modes, the offline eval harness with its rendered report, live cluster deployment and verification, the graduation chain export → train → evaluate → package → graduate, the two-layer gate with blocked-request metadata logging (gate-blocks.jsonl beside the decision log), and the synthetic sensitivity dataset builder with its fakeness-checked generator.

What is still ahead

Your own traffic. Everything above runs offline against fixtures and the shipped eval set; the cutover itself waits for a real decision log — see the refusal box, which is the correct behaviour until that happens.

Refuses, by design

graduate runs the whole chain offline and answers NOT READY on the 223-decision teacher log: 47.6% tier agreement against a 0.95 floor, ECE 0.28 against 0.10, 48 held-out rows against a 500 minimum. Exit 1, nothing written. Graduation is wired end to end and says no until there is enough real logged traffic — which is the only acceptable behaviour for a gate on the cutover path.
